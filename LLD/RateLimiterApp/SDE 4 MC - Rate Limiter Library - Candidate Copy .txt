Problem Statement
Design and implement an in-process Rate Limiter library that throttles requests based on configurable rules. A driver class should demonstrate all functionality.
________________


Core Concepts
Request
* key (string) — identifies who/what is rate-limited (e.g., client ID).
* cost (int, default 1) — for weighted limiting (e.g., bulk call = 5 units).
RateLimitResult
* status: ALLOWED | THROTTLED
* evaluatedAt: timestamp
* throttledByRule: rule name that blocked it (null if allowed)
* remainingQuota: tokens/requests left
* retryAfterMs: suggested wait before retry (0 if allowed)
________________


Requirements
1. Rate Limiter
* Initialized with a named configuration (see below). Multiple named limiters per app.
* Has one or more Rules. All rules must pass for a request to be ALLOWED (AND semantics).
* Returns a RateLimitResult enriched with a timestamp.
* Supports two modes:
   * Non-blocking: returns immediately.
   * Blocking: waits up to max_wait_timeout_ms for quota; returns THROTTLED on timeout.
* Thread-safe. No over-admission under concurrency. No data loss.
2. Rules & Strategies
Each rule has a strategy (algorithm) and a scope: GLOBAL (shared across all keys) or PER_KEY (independent per key).
Implement at least two of:

	Behavior

Request(cost=1) → ALLOWED  → [●○○○○]  1 token left
Request(cost=1) → ALLOWED  → [○○○○○]  0 tokens left
Request(cost=1) → THROTTLED (0 tokens, retryAfter=500ms)

Time 3.500s:  [●●●●●]  → 5 tokens (full, won't exceed capacity)


Request(cost=6) → THROTTLED (cost > capacity, can NEVER succeed)




3. Observers
* Register one or more observers notified asynchronously on every decision (must not block the critical path).
* ConsoleObserver: prints each decision to STDOUT.
* MetricsObserver: tracks allowed/throttled counts per key per rule. Exposes a dump() method. (Good to Have)
________________


Sample Config
limiter_name: api-gateway-limiter
mode: NON_BLOCKING
rules:
  - rule_name: global-throughput
    strategy: FIXED_WINDOW
    scope: GLOBAL

Evaluation Scenarios (demonstrate in Driver class)
1. Basic throttling — Fixed Window (5 req/10s, PER_KEY). Send 7 requests → first 5 ALLOWED, last 2 THROTTLED.
2. Rule composition — GLOBAL Fixed Window (10 req/min) + PER_KEY Token Bucket (cap=3, refill=1/s). Per-key limit hits first; global limit hits when many users exhaust it collectively.
3. Concurrency — 10 threads, same key. Total allowed must never exceed the limit.
4. Blocking mode — Token Bucket (cap=2, refill=1/s), max_wait=3s. Show a blocked request eventually ALLOWED after refill; show THROTTLED when timeout expires.
5. Weighted requests — Costs of 1, 5, 10. A cost=10 request against capacity=8 → immediate THROTTLED.
6. Metrics dump — After a batch, call MetricsObserver.dump() to show per-key/per-rule counts.
________________


Guidelines
* Use in-memory data structures only. No external DB, queue, cache, or rate-limiting library.
* Driver class executes everything — no console/file input.
* Prioritize compilation, execution, and correctness.
________________


Bonus (if time permits)
* Hierarchical keys (e.g., tenant:user) with per-level limits.
* Stale per-key state cleanup to prevent memory leaks.
